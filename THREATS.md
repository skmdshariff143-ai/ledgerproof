# THREATS

Only threats with a passing test are listed. Tests named `THREAT ...` live in:
- `api/test/schema.test.js`: database defenses.
- `api/test/transfer.test.js`: the `transfer()` service.
- `api/test/auth.test.js`: HTTP authentication, roles, ownership and audit, tested against a running server.
- `api/test/roles.test.js` and `api/test/proxy.test.js`: the restricted database role and the trusted-proxy setting. Every API test also runs as that restricted role.
- `api/test/revocation-fail-closed.test.js` and `api/test/readiness.test.js`: fail-closed token revocation and the public readiness answer, tested with a fake database pool.
- `api/test/cross-instance-revocation.test.js`: logout through one API process, refusal by another.
- `api/test/audit-chain-concurrency.test.js`: 30 audited requests at once, then chain verification.
- `api/test/account-state.test.js`: freeze and unfreeze cannot activate a pending-KYC account.
- `api/test/audit-function-consistency.test.js`: the function definitions, upgrade behaviour, id gaps, and tampering of each position in the chain.

## Ledger and money movement

| Threat | API defense | DB defense | Test |
|---|---|---|---|
| Books go out of balance (debits != credits) | `transfer()` always writes one debit and one credit of the same amount | Deferred constraint trigger `ledger_entries_balanced` rejects the transaction at COMMIT | `THREAT unbalanced books` |
| Zero or negative amounts | `validate()` rejects non-integer, zero and negative amounts with 400 | `CHECK (amount_paise > 0)` | `THREAT bad amounts` |
| Past ledger rows edited or deleted | No route updates or deletes ledger rows, and the API's database role has no UPDATE or DELETE on them | Triggers block UPDATE, DELETE, TRUNCATE on `ledger_entries` | `THREAT tampering: ledger entries` |
| Same request pays twice | `transfer()` stores the key in the same transaction as the money and replays the first answer | `idempotency_keys (user_id, key)` is the primary key | `THREAT double payment` |
| Overdraft: spend more than the balance | `transfer()` checks the locked `balance_paise`; only the `system_vault` may go below zero | `CHECK user_balance_not_negative` on `accounts` | `THREAT overdraft`, `THREAT overdraft at the database` |
| Overdraft by racing requests | Both account rows are locked (`FOR NO KEY UPDATE`) before the balance is read | balance UPDATE in `ledger_entries_apply` row-locks the account; `user_balance_not_negative` | `THREAT concurrent overdraft` |
| 20 simultaneous withdrawals of Rs 1,000 from Rs 5,000 overdraw the account | Both account rows locked before the balance is read; losers get a clean 422 `INSUFFICIENT_FUNDS`, never a 500 | `user_balance_not_negative` | `THREAT concurrent overdraft over HTTP` (concurrency.test.js: exactly 5 succeed, balance 0, reconcile balanced) |
| Alice->Bob and Bob->Alice at the same moment deadlock and lose a request | Locks taken in ascending id order in one statement | none | `THREAT cross-transfer deadlock over HTTP` (concurrency.test.js: 30 requests all 201, money conserved, reconcile balanced) |
| THREATS.md names a test that does not exist, or a THREAT test is missing from THREATS.md | none | none | `THREATS.md lists threats`, `every test named in THREATS.md exists`, `every THREAT test is listed in THREATS.md` (threats.test.js) |
| Balance edited directly, or account opened with money | none (no API writes balances) | `accounts_guard`: `balance_paise` changes only from the ledger trigger; accounts open at zero | `THREAT balance forgery` |
| Cached balance or running balance drifts from the ledger | none | `ledger_entries_apply` computes both on insert and overwrites client values | `running balance is set by the database...`, `transaction type is derived ... balance_paise matches the ledger` |
| Account reassigned to another owner, turned into the vault, or the vault deleted and replaced | none | `accounts_guard`: `owner_id`, `account_type`, `account_number` immutable; accounts cannot be deleted | `THREAT ownership change` |
| Second money source, ownerless user account, unknown role | none | partial unique index `accounts_single_vault`; `vault_has_no_owner`; `users_role_check` | `THREAT second vault, ownerless user account or unknown role` |
| Money moved on a frozen account | `transfer()` returns `ACCOUNT_FROZEN` | `ledger_entries_apply` rejects entries on non-active accounts | `THREAT frozen account`, `THREAT frozen account at the database` |
| Bad input (fractional, zero, negative, same account, unknown account) | `validate()` and account lookups | `CHECK (amount_paise > 0)` | `THREAT bad input` |
| Same request sent twice | Existing key returns the original transaction (`replayed: true` from `transfer()`; over HTTP the same 201 body plus `Idempotent-Replayed`) | primary key `idempotency_keys (user_id, key)` | `THREAT double payment: replaying` |
| Same key reused for a different request | Request hash compared, `IDEMPOTENCY_CONFLICT` | none | `THREAT key reuse` |
| Same request sent in parallel | Key row is the last write, so the losing request rolls back and returns the winner's result | primary key `idempotency_keys (user_id, key)` | `THREAT concurrent double payment` |
| Deadlock between opposite transfers | Both accounts locked in one statement, ascending id order, `FOR NO KEY UPDATE` | none | `THREAT lock order` (holds the lower id and shows the waiting transfer has not locked the higher one; fails if the ORDER BY id is removed) and `opposite-direction parallel transfers do not deadlock` |

| Database default isolation weakens the overdraft check | Transaction starts with `ISOLATION LEVEL READ COMMITTED` | none | `THREAT isolation` |
| Malformed or case-variant account ids, oversized keys | `isUuid()` requires lowercase UUID strings (an array of one id no longer passes as text) and key length <= 200 | uuid column types | `THREAT malformed ids` |

Known gaps:
- The schema owner (used only to load the schema and run the seed) can still drop the triggers. The API connects as `ledgerproof_app`, which cannot.
- `accounts_guard` still trusts `pg_trigger_depth() >= 2` to recognise the ledger trigger. That is safe only because no role except the schema owner may update balances; `THREAT temp trigger mint` is the test that keeps it so.
- `transfer()` itself does not check ownership; the HTTP route does. Any new caller of `transfer()` must authorize first.
- Paying by account number reveals two things to a user who has funds: whether a number exists (404 for unknown) and whether its account is frozen (422 `ACCOUNT_FROZEN`, after the funds check). Account numbers are meant to be shared with payers and a sender needs to learn why a payment failed, so this is accepted rather than hidden. It exposes no balances or owners. Found by the security audit; the owner may choose to return one generic error instead.
- The browser app keeps the login token in `sessionStorage`, readable by any script on the page. Mitigation: all text goes through React, and the source contains no `dangerouslySetInnerHTML`, `innerHTML` or `eval` (checked by searching `web/src`, not by an automated test). A strict Content-Security-Policy is set by `web/vercel.json`; it was seen as a response header on the live site and caused no console violations in a browser, but no automated test covers it.
- The browser app has no end-to-end tests; it was checked by hand in a browser for all four roles. Only the money helpers have automated tests.
- The restricted role stops edits to balances, roles, owners and history, but it must be able to INSERT into the ledger, transactions, idempotency and audit tables. Anyone who could run arbitrary SQL as that role (through an SQL injection or a leaked connection string) could insert forged but balanced ledger rows, audit rows or idempotency keys, though not choose their ids or timestamps. All SQL in the API uses bound parameters, and reconcile would still show a ledger that does not match the stored balances, but the role cannot prevent forged inserts by design.
- A database session can still create temp tables (PUBLIC has that right on every Postgres database). The functions that read tables pin their `search_path` so temp tables cannot shadow them, but queries typed by someone with SQL access to the app role are not protected from that.
- The pinned Supabase root CA expires on 2031-04-26; a test fails once fewer than 90 days remain. Supabase could also rotate its CA earlier, which would stop database connections until the certificate in `api/src/supabase-ca.js` is replaced.
- Rate limiting is enforced on `/api/auth/login` and `/api/auth/register` (using `rate_limit_buckets` in PostgreSQL once migrated, with an in-memory per-instance fallback if the table is not yet present); money movement routes and `GET /api/ledger/reconcile` do not yet enforce per-IP rate limits.
- Reconcile scans the whole ledger and its `problems` list is not capped.
- No `lock_timeout` or `statement_timeout` is set yet.
